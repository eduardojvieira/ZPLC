# Kconfig options

The ZPLC runtime module defines 40 Kconfig symbols. Set one in the `prj.conf` of an application or in a board overlay as `CONFIG_<SYMBOL>=value`; a symbol that depends on another is available only while that one is enabled.

This table is read off the source file `firmware/zephyr/Kconfig`; its text is the source's own, so it is the same in English and in Spanish.

| Symbol | Type | Default | Range | Depends on | Description |
| --- | --- | --- | --- | --- | --- |
| `CONFIG_ZPLC` | `bool` |   |   |   | Enable the ZPLC IEC 61131-3 PLC runtime. This provides a portable virtual machine for executing PLC programs compiled to the .zplc bytecode format. |
| `CONFIG_ZPLC_STACK_DEPTH` | `int` | `256` | `8` to `4096` | `CONFIG_ZPLC` | Maximum depth of the VM evaluation stack. Each entry is 4 bytes (32-bit), and every registered task has its own stack. The stack pointer is 16 bits wide; the upper end of the range is a RAM limit long before it is a type limit. |
| `CONFIG_ZPLC_CALL_STACK_DEPTH` | `int` | `32` | `1` to `255` | `CONFIG_ZPLC` | Maximum call nesting depth for subroutines. The call depth is an 8-bit counter, so 255 is the largest value the VM can hold. |
| `CONFIG_ZPLC_WORK_MEMORY_SIZE` | `int` | `8192` | `16` to `8192` | `CONFIG_ZPLC` | Size of the work memory region for temporary variables. The region owns the 8 KB window 0x2000..0x3FFF of the PLC address space; a larger value would only waste RAM and is refused. |
| `CONFIG_ZPLC_RETAIN_MEMORY_SIZE` | `int` | `4096` | `16` to `4096` | `CONFIG_ZPLC` | Size of the retentive memory region. The region owns the 4 KB window 0x4000..0x4FFF of the PLC address space. This memory is persisted across power cycles only when ZPLC_RETAIN_PERSIST is enabled. |
| `CONFIG_ZPLC_CODE_SIZE_MAX` | `int` | `45056` | `128` to `45056` | `CONFIG_ZPLC` | Largest artifact the runtime accepts, in bytes. This one value is the code region of the VM, the largest artifact the program store keeps and restores (RT-028), the size of the staging buffers and the size the shell and the IDE handshake advertise. Program addresses are 16 bits wide and the code region starts at 0x5000, so 45056 (0xB000) is the largest value. Two program slots of this size have to fit the storage partition of the board together with the RETAIN records; the build fails when they do not. |
| `CONFIG_ZPLC_FAILSAFE` | `bool` | `y` |   | `CONFIG_ZPLC` | Reads the reset cause at boot (power-on, brown-out, pin, software, watchdog or fault, wherever the processor reports it), so that the status shows why the runtime is in STOP (RT-021). The cause is reported by `zplc sys reset`. A part whose hardware-information driver has no reset-cause register reports "unknown". The record of a fault that survives a reset is kept in every build. |
| `CONFIG_ZPLC_FATAL_HANDLER` | `bool` | `y` |   | `CONFIG_ZPLC` | Replaces the kernel's fatal-error handler: on a processor fault, a stack overflow or a kernel panic the outputs are driven to their safe state, the reason is recorded and the board reboots into STOP (RT-019). Without it the kernel halts with the outputs wherever the last scan left them. Turn it off only for a board that has a handler of its own. |
| `CONFIG_ZPLC_REQUIRED_GPIO_OUTPUT_MASK` | `hex` | `0x0` | `0x0` to `0xF` | `CONFIG_ZPLC` | Bit mask of digital outputs, counted from the first output of the I/O table, that must be configured from DeviceTree for the Zephyr HAL to initialize, in addition to the channels the board description marks as required. The I/O description of a listed board already requires every channel it lists; this mask is for a profile without a description (the default alias profile). A missing or unconfigurable required channel fails HAL initialization; this setting does not qualify the electrical behavior of any mapped pin. |
| `CONFIG_ZPLC_IO_INPUT_IMAGE_BYTES` | `int` | `0` | `0` to `4080` | `CONFIG_ZPLC` | Bytes of the input process image that the channels of the board use. 0 takes the size from the board I/O description in firmware/app/boards/boards.json (the highest input channel plus its width); a larger value reserves room for channels added later. The build fails when the value is smaller than the channels need or reaches the system registers at the end of the 4 KB input image. The memory the image occupies is still the 4 KB of the instruction set: shrinking it is a change of the binary contract. |
| `CONFIG_ZPLC_IO_OUTPUT_IMAGE_BYTES` | `int` | `0` | `0` to `4096` | `CONFIG_ZPLC` | Bytes of the output process image that the channels of the board use, derived from the board I/O description when 0. The build fails when the value is smaller than the channels need. |
| `CONFIG_ZPLC_PROGRAM_STORE_CHUNK_SIZE` | `int` | `1024` | `256` to `2048` | `CONFIG_ZPLC` | The program store cuts the artifact into chunks of this size and keeps each under its own key, because a flash key-value store holds one entry inside one erase sector and an artifact as large as ZPLC_CODE_SIZE_MAX (45056 bytes by default) does not fit a 4 KB sector. An artifact of at most one chunk is one key, which is the layout of the first version of the store. A chunk and the entry overhead of the backend must fit a sector with room for its allocation records: 1024 fits the 4 KB sector of every board of this repository. The build checks that the storage partition holds two slots of ZPLC_CODE_SIZE_MAX in chunks of this size. |
| `CONFIG_ZPLC_EXCHANGE_QUEUE_BYTES` | `int` | `1024` | `256` to `16384` | `CONFIG_ZPLC` | A write from a thread outside the scan (Modbus, MQTT, the shell) is queued whole and applied at the input latch of the next scan (RT-010). Each queued write takes its data and four bytes of header. A write that does not fit is refused, with nothing queued, and the caller sees an error: a Modbus TCP client gets exception 6 (server device busy). The default holds a Modbus write of 100 mapped registers. The exchange also keeps one copy of IPI, OPI, WORK and RETAIN, the snapshot a reader sees, so it costs the sum of the four region sizes of RAM besides this queue. |
| `CONFIG_ZPLC_VM_CYCLE_INSTRUCTION_BUDGET` | `int` | `100000` | `1` to `10000000` | `CONFIG_ZPLC` | Maximum VM instructions permitted in one production PLC scan. Reaching the limit is a controlled logical VM watchdog fault. It is not a physical watchdog, timing measurement, or WCET guarantee. |
| `CONFIG_ZPLC_LOG_LEVEL` | `int` | `3` | `0` to `4` | `CONFIG_ZPLC` | Log level for ZPLC runtime. 0=OFF, 1=ERR, 2=WRN, 3=INF, 4=DBG |
| `CONFIG_ZPLC_COMM_THREAD_PRIORITY` | `int` | `8` | `1` to `14` | `CONFIG_ZPLC` | Preemptible priority of every thread the application creates to talk to the outside: the MQTT client, the Modbus TCP server, the Modbus clients and the function-block workers. The scan coordinator (the high-priority work queue, or the normal one when there is none) must have a lower number, so that a communication thread never delays a scan (RT-013); the build fails otherwise. Zephyr's shell and log threads run at the lowest application priority unless the build overrides them, and the same rule is checked against the override. |
| `CONFIG_ZPLC_SCHEDULER` | `bool` | `n` |   | `CONFIG_ZPLC` | Enable the ZPLC multitask scheduler. Allows running multiple PLC tasks with different intervals and priorities using Zephyr's k_timer and work queue system. |
| `CONFIG_ZPLC_HARDWARE_WATCHDOG` | `bool` | `n` |   | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_WATCHDOG` | Arms the Zephyr watchdog only while a ZPLC scheduler batch completes input snapshot, all due tasks, deadline checks, and one normal output commit. It is never fed by an ISR, timer, shell, network, or idle path. This default is intentionally off. Enable it only in an exact board/revision profile after HIL has verified watchdog reset timing and safe outputs. The VM instruction budget remains a logical fault limit; it is not this physical watchdog. |
| `CONFIG_ZPLC_HARDWARE_WATCHDOG_TIMEOUT_MS` | `int` | `1000` | `100` to `60000` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_HARDWARE_WATCHDOG` | The timeout the profile's reset timing was recorded at (HIL-010): the watchdog is never armed with a shorter one. This setting has no evidence value until HIL verifies the selected device. A task set whose slowest interval is over half of this is given a longer timeout, up to ZPLC_HARDWARE_WATCHDOG_TIMEOUT_MAX_MS, so the timeout follows the tasks; a task set that does not fit is refused at START. |
| `CONFIG_ZPLC_HARDWARE_WATCHDOG_TIMEOUT_MAX_MS` | `int` | `8000` | `100` to `60000` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_HARDWARE_WATCHDOG` | A property of the part (its counter width and clock). The timeout for a task set is never longer than this. |
| `CONFIG_ZPLC_WATCHDOG_STOP_FEED` | `bool` |   |   | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_HARDWARE_WATCHDOG` | A watchdog that cannot be stopped once started has to be fed while the runtime waits in STOP, or the board resets. The default is to disarm it in STOP. Fed from the control path of the scheduler, never by a timer that survives a hung scan. |
| `CONFIG_ZPLC_WATCHDOG_PAUSE_DISARM` | `bool` |   |   | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_HARDWARE_WATCHDOG` | The default is to keep the watchdog fed from the control path while the runtime is paused or stopped at a breakpoint, so that a long breakpoint does not reset the board. Disarm it instead on a part whose watchdog can be stopped and for which a long breakpoint is a normal part of debugging. |
| `CONFIG_ZPLC_WATCHDOG_FAULT_DISARM` | `bool` |   |   | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_HARDWARE_WATCHDOG` | The default is to leave the watchdog armed and unfed in a latched fault: it resets the board into STOP with the cause recorded, so that the reset does not erase the fault and a person sees why. Disarm it instead to keep the board latched in the fault until a program is loaded. |
| `CONFIG_ZPLC_DEADLINE_MISS_LIMIT` | `int` | `3` | `1` to `1000000` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER` | A task misses its deadline when a scan ends more than one interval after its release. A miss raises the warning, is counted and its overrun is recorded (RT-014). This many misses of the same task in a row latch the fault: the outputs go to their safe state and a program has to be loaded or the runtime reset. A scan in time ends the run of misses. The default of three tolerates one late activation, which a communication burst or a flash write can cause, and still stops a scan that does not fit its interval. 1 latches at the first miss. This value is a design default until a board's timing record states another (HIL-010). |
| `CONFIG_ZPLC_MAX_TASKS` | `int` | `8` | `2` to `16` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER` | Maximum number of PLC tasks that can be registered. Each task requires approximately 1KB of RAM for its VM state. |

| `CONFIG_ZPLC_SCHED_HIGH_PRIO_WORKQ` | `bool` | `y` |   | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER` | Run the single scheduler batch coordinator on a dedicated high-priority work queue. Task ordering remains deterministic within each batch. |
| `CONFIG_ZPLC_SCHED_HIGH_PRIO_STACK_SIZE` | `int` | `2048` | `1024` to `16384` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_SCHED_HIGH_PRIO_WORKQ` | Stack size for the high-priority work queue thread. |
| `CONFIG_ZPLC_SCHED_HIGH_PRIO_PRIORITY` | `int` | `2` | `0` to `14` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_SCHED_HIGH_PRIO_WORKQ` | Priority of the high-priority work queue thread. Must be lower (higher priority) than ZPLC_SCHED_WORKQ_PRIORITY; the build fails otherwise. |
| `CONFIG_ZPLC_RETAIN_PERSIST` | `bool` |   |   | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_SCHED_HIGH_PRIO_WORKQ` | Off by default: the flash write path has been exercised on native_sim and QEMU only, and on several boards the storage partition is also used by another file system. Turn it on for a board once that board has passed its hardware record (HIL-010). Restores the RETAIN region when a program is loaded or restored at boot, before the first scan, and stores it on STOP and periodically while the program runs. A record carries a checksum, a layout hash and the program identity, two records alternate, and a record is restored only when both the identity and the layout match; otherwise the region is initialised and the status says why. The stores go through zplc_hal_persist_*, so this needs a working persistence backend (CONFIG_NVS on the boards of this repository). Periodic saves run on the normal-priority scheduler work queue, never in the scan batch and never with the memory lock held. Whether a flash write stalls the scan depends on the flash driver and has not been measured on any board: see docs/docs/runtime/persistence.md. |
| `CONFIG_ZPLC_RETAIN_SAVE_INTERVAL_S` | `int` | `3600` | `0` to `86400` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_RETAIN_PERSIST` | A running program stores its RETAIN region at most once per interval, and only when the region changed. 0 turns periodic saves off: only STOP stores. The default is deliberately long: a board states its own numbers in its board file to earn a shorter interval. |
| `CONFIG_ZPLC_RETAIN_FLASH_ENDURANCE_CYCLES` | `int` | `10000` | `100` to `1000000000` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_RETAIN_PERSIST` | From the datasheet of the part that holds the storage partition. | `CONFIG_ZPLC_RETAIN_FLASH_WEAR_BYTES` | `int` | `40000` | `1024` to `1000000000` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_RETAIN_PERSIST` | (sectors - 1) * sector size, minus the live data that garbage collection copies at every rotation (the two program slots, about 8300 bytes). One sector is always kept free for garbage collection. |
| `CONFIG_ZPLC_RETAIN_ENTRY_OVERHEAD` | `int` | `64` | `0` to `4096` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_RETAIN_PERSIST` | Entry header and alignment of one chunk: 8 bytes for the NVS allocation entry, a data CRC if enabled, and the padding to the flash write block. The default covers a 32-byte write block. |
| `CONFIG_ZPLC_RETAIN_LIFE_YEARS` | `int` | `10` | `1` to `50` | `CONFIG_ZPLC`, `CONFIG_ZPLC_SCHEDULER`, `CONFIG_ZPLC_RETAIN_PERSIST` | Flash life the save interval must reach (years) |

A chunk plus the backend overhead must fit one erase sector minus four allocation entries (the NVS limit): 1024 fits a 4 KB sector. The region needs at most eight chunks. |
| `CONFIG_ZPLC_MQTT_ALLOW_INSECURE_TLS` | `bool` | `n` |   | `CONFIG_ZPLC` | Off by default (COM-014). With it off, `zplc config set mqtt_security 1` is refused and a stored value of 1 stops the client from connecting, so a release image can never run a TLS session that does not authenticate the broker. With it on, setting `mqtt_security 1` is the explicit opt-in, and `zplc mqtt status` and `zplc status` show tls-verify OFF for as long as the session is configured that way. Use it for a bench against a broker with a self-signed certificate that you cannot install a CA for. |
| `CONFIG_ZPLC_SHELL_RAW_MEMORY` | `bool` | `n` |   | `CONFIG_ZPLC`, `CONFIG_SHELL` | Off by default (COM-022). The diagnostic image sets this and CONFIG_DEVMEM_SHELL=y together (firmware/app/diagnostic.conf). The application build stops with an error when CONFIG_DEVMEM_SHELL is on and this is off, so the one cannot be switched on by accident behind the other. |
| `CONFIG_ZPLC_HIL_DEBUG` | `bool` | `n` |   | `CONFIG_ZPLC` | Enables Hardware-in-the-Loop debugging features. Adds JSON trace output for VM introspection and testing. When enabled, the runtime emits structured JSON debug frames over serial for automated testing and validation. |
