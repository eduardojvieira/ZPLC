# PUB-005: how the site turns to 2.1 with the release (proposal)

**Status**: proposal for the owner. Nothing in it is changed by this unit: no workflow, no site configuration, no page.

PUB-005 asks that "the site MUST change to 2.1 by the release itself and not before, so that what a visitor reads is what they can download", and that the run propose how, before the first candidate.

## 1. What the site does today (measured at `b3cde14d`)

The handoff measured at `77dfb9af`. Measured again here:

How a release is made today, for comparison: `.github/workflows/release.yml` runs on a `v*` tag push, builds every platform and creates a **draft** release; a person publishes the draft after the first-run checks. `.github/workflows/update-channels.yml` already runs on `release: types: [published]`, the moment a person publishes.

So the gap PUB-005 names holds: the merge of the release branch into `master` touches `docs/` and `packages/zplc-ide/`, so it deploys the 2.1 pages while the Latest release is still 2.0.1, under a label that says "2.0". The footer is the only part that follows the release, and it follows it only at the next deploy.

## 2. Recommendation

**Publish the site on the publication of a release, from the tree of its tag, and take the version label from that tag. Do not keep the 2.0 pages as a Docusaurus version.**

1. **Trigger.** `deploy-docs.yml` deploys on `release: types: [published]` (the same event `update-channels.yml` uses), checking out the tag of that release. A push to `master` and a pull request still build the site and run every check, but no longer deploy. `workflow_dispatch` stays, with a required input `tag` that must name a published release (checked with `gh release view`), for a fix of the site between releases. Prereleases (`-rc.`) do not deploy: the job runs only when `github.event.release.prerelease` is false, or when a person dispatches it.
2. **Label.** The label of line 106 is computed, like the footer, from `ZPLC_RELEASE_TAG` (`v2.1.0` gives `2.1`), with the `package.json` version as the fallback for a local build. Nothing about the version is written by hand any more; a check in `tools/docs/check-docs-config.test.ts` pins that the label and the footer come from the same tag.
3. **2.0 pages.** Not kept as a versioned copy. The 2.0 documentation stays readable where it already is, in the tree of the `v2.0.1` tag on GitHub, and the release notes page keeps a section per release (2.1.0 at the top, 2.0.x below), which PUB-002 and OSS-004 already require. The page "what is new in 2.1" (PUB-002) carries the steps from 2.0.

## 3. Trade-offs

| Choice                                   | For                                                                                                                                                       | Against                                                                                                                                                                                                                                       |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deploy on `release: published` (chosen)  | The site changes at the one act that makes 2.1 downloadable, a person publishing the draft, with no step to remember. The site is built from the exact tree of the release (PUB-003). Same event as the install channels. | A fix to a page between releases no longer reaches the site by itself: it needs a patch release or the dispatch with a tag. The site is built from the tag, so a fix on `master` is published only with the next tag, or by a tag made for it. |
| Deploy on the `v*` tag push              | Earlier than publication, already the release trigger.                                                                                                    | The tag exists while the release is still a draft, during the first-run checks, sometimes for days: the site would show 2.1 before anyone can download it. That breaks PUB-005.                                                              |
| Keep the push to `master`, gate by hand  | No change to the workflow.                                                                                                                                | Exactly the present failure: it depends on a person not merging, or on the merge waiting until after publication.                                                                                                                             |
| No versioned copy of 2.0 (chosen)        | One tree of pages, in two languages, as today. The parity check, the generated references, the search index and the link check run once.                | A 2.0 user reads 2.1 pages. the cost is small as long as 2.1 opens 2.0 projects, which the migration steps of PUB-002 must state (not verified by this unit); the 2.0 pages remain on GitHub at the tag.                                                             |
| Docusaurus `docs:version 2.0`            | A visitor on 2.0 picks its version from a dropdown.                                                                                                       | It copies 331 pages in English and 331 in Spanish (about 5.7 MB) into `versioned_docs/`, and they must keep passing the parity, link, capability-claim and search checks; the generated reference pages of 2.0 are frozen beside the new ones. The hand label problem moves into `versions.json`. |

## 4. The files a later unit changes

When the owner accepts this, one unit with its tests changes:

- `.github/workflows/deploy-docs.yml`: add `release: types: [published]`; make the `deploy` job run on that event and on `workflow_dispatch` only; check out `github.event.release.tag_name` (or the dispatched `tag`); skip prereleases; read `ZPLC_RELEASE_TAG` from the event instead of the latest-release lookup when the event has it.
- `docs/docusaurus.config.js`: compute `versions.current.label` from `releaseTag` (line 106), next to the footer's `releaseTag` (lines 12-15).
- `tools/docs/check-docs-config.test.ts`: the label and the footer name the same release, and no version label is a literal.
- `tools/ci/ci-workflow.test.ts`: `deploy-docs.yml` deploys only on a published release or a dispatch with a tag.
- `docs/docs/release-notes/index.md` and `docs/i18n/es/docusaurus-plugin-content-docs/current/release-notes/index.md`: a 2.1.0 section above the 2.0 one (with OSS-004 and PUB-002, not in the same unit).
- `docs/src/components/LandingPage/content.js`: the first screen that says what 2.1 adds, with the plant in motion (PUB-004, a unit of its own).

After the release, the check PUB-005 asks for (the public address opened, the version shown, each install link, both languages, the search) is recorded in the release evidence of spec 014; it is not part of this change.
